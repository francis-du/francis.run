wcode 0.9.0：开始认真处理多 Agent 协作

最近我同时推进几个项目，Agent 也拆成了几路。有人修后端，有人做界面，有人盯着 PR 和 CI。并行确实快了，但一轮下来，最费心的往往是收尾：谁改了哪些文件，哪些结果还能复用，合到一起以后到底有没有测过。

这也是 wcode 0.9.0 这一轮主要在处理的事情。

如果你第一次看到这个项目，wcode 是我用 Rust 做的一套 Coding Agent 工具。通过 MCP 接到现有的编码助手上，帮它读仓库、找代码、修改文件和运行检查。任务、文件版本和验证结果会留在 wcode 里，换一个模型继续做，也能从这些状态接下去。

0.8 花了不少时间整理代码图谱、架构和证据。到了 0.9，我更想把实际干活的过程接顺：几个 Agent 怎么分工，人怎么知道它们做到了哪一步。

分任务的时候，把文件范围一起分出去#

让三个 Agent 分别做实现、测试和文档，听上去很清楚。问题是，它们可能最后都要改同一个文件。

0.9 的 Worklist 给任务加了明确的写入范围。比如界面任务负责 src/ui/，后端任务负责 src/runtime/，审查任务的 write_paths 留空，按只读任务处理。领取时会核对任务依赖和当前版本；如果另一项活跃领取包含重叠的写入范围，本次领取会被拒绝。

Worker 调用 worklist_claim 领取任务，拿到自己的令牌和交接包。任务租约是 15 分钟，长任务需要续租；完成以后用 worklist_submit 提交结果，以及已经产生的证据引用。主 Agent 可以看各路汇总，再决定怎么接下一步。

这里有个很实际的区别：wcode 管协作状态，启动 Agent 仍然由你正在用的宿主负责。 Codex、Claude Code 等宿主有自己的模型和子 Agent 能力，不需要为了用 Worklist 再换一套模型平台。

我也没有让任务领取变成新的授权入口。领到了 src/ui/ 的任务，后面的文件修改照样核对 SHA，执行命令照样走原来的权限。另一个会话已经把文件改了，就重新读，不能拿旧交接包直接覆盖。

这套流程的用处，在多人或多会话同时动一个仓库时尤其明显。分工有记录，冲突有位置，任务交回来时也知道它针对哪个版本。

打开工作台，先看到现在该处理什么#

以前 wcode 已经能展示架构、代码关系、任务和验证，但要判断“接下来做什么”，还是得在几个页面之间找。

0.9 把当前问题收到了同一份列表里：失败的检查、还没完成的验证、互相矛盾的证据、缺失的设计映射，以及需要继续看的风险。点进去，就到对应的任务、源码或验证视图。

截图来自 0.9.0 开发版本，使用演示项目数据。

我想让第一屏回答得更直接一点：现在卡在哪里？这件事归谁？要看哪份结果？至于完整代码图谱、历史和详细指标，沿着问题再往下看就好。

当前工作区、源码版本和快照状态也留在页面上。切到任务页或文件页以后，不用凭刚才的记忆判断自己正在看哪个项目。缓存还在刷新，或者某个 Provider 暂时没有数据，界面就照实显示。

终端里的观测台也补了概览、问题、任务、Provider 和 Agent 导航。窄窗口优先留下任务和恢复操作，详细内容再展开。一直开着它的时候，我最想及时看到的是阻塞和待处理事项。

看源码，能顺着看，也知道有没有过期#

有些问题最终还是得回到源码。

0.9 可以从文件树和大型模块入口打开实际代码，按行分页。页面绑定读取时的源码 SHA；翻页时文件已经变了，就要求重新读取。

这在并行修改时很有用。假设我正看一个函数，另一个 Agent 刚改了文件后半段，下一页就不能悄悄拼上新版本。否则屏幕上看起来是一份完整文件，实际却混了两个时间点。

同样，切换工作区或换了查询以后，迟到的请求也不能把刚打开的页面覆盖掉。代码查看器需要和编辑器一样认真对待版本。

上下文少重复一点，交接也轻一点#

多 Agent 的另一个开销是反复解释同一个仓库。

每开一路任务，都重新扫描、读一遍说明、再找一遍工具，很快就会把上下文花在重复信息上。0.9 的交接包可以复用仍然有效的任务上下文，只补缺失或过期的部分。

工具信息也做了整理。任务需要哪些工具，保留标准工具名和必要参数；可以重新取得的路由说明、重复的默认工作区指引，少传几次。真正要编辑的源码正文、SHA、相关检查和失败状态仍然保留。

我关心的是 Agent 拿到这份上下文以后能不能继续干活。少几个字段却让它重新问一轮、再读一遍文件，算不上省。

这一轮也在修并发下的实际等待：相同验证可以合并执行，各个仓库的记录写入则按工作区隔离。一个项目在写记录，不应该把另一个项目的查询也堵住。

最后合在一起的版本，还得自己验一次#

各路 Worker 报告完成以后，工作还没有结束。

一个任务测的是它修改时的版本，另一个任务又可能改了相关文件。主 Agent 收到结果以后，需要对合并后的当前代码重新审查和验证。旧的绿色结果可以供参考，不能直接批准新版本。

0.9 的 Change Acceptance 正在把这一步整理成可读取的记录：当前 Git 版本、项目要求、实际执行的检查，以及还缺什么。已经实现的本地检查可以明确给出阻塞原因；面向团队的远端合并流程还要继续做实际部署验收。

我希望最后看到“可以合并”的时候，能顺着记录找到它的依据，而不是再问几个 Agent 一遍“你确定做完了吗”。

目前源码版本已是 0.9.0，公开发布包仍是 0.8.5，0.9.0 还在发布前验证。新版本进度可以看 GitHub，具体命令和接入方式在 项目网站；这一版的功能记录放在 0.9.0 文档。
