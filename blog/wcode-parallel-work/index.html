把 wcode 放到并行工作里，几个小问题就暴露了

4 分钟阅读1852 字

最近我把几个 Rust 项目一起放进了并行迭代。一个 Agent 看一个项目，修已有 PR，补回归，跑对抗检查，再继续处理没做完的东西。

这种用法对 wcode 挺合适，也挺不客气。

单个请求能顺利完成的时候，一些问题很难看出来。等几个 Agent 同时读上下文、找验证工具、检查缓存，线程池和锁之间的关系就开始变得很具体。用户看到的可能只是一个转了很久的加载状态，底下却有好几层等待。

这轮有三个地方值得单独记一下。相关修改都在 PR #4。

等验证的人，也会占着资源#

wcode 会合并同一个项目的一些验证工作，避免几个请求同时把相同的构建再跑一遍。这本来是个很自然的优化。

麻烦在等待者身上。它可能已经拿到了一个工具执行名额，然后等另一位调用者完成验证。持有验证锁的那位又可能暂时挂在别的线程池工作里。只看各自那段代码，很容易觉得“等一下就好了”。

我现在给普通原生调用者的等待设了五秒上限。超时就明确返回 busy，让调用者稍后再试。处在 Rayon worker 上时，则直接拒绝继续等待，避免把线程池里本来就有限的工人一起堵住。

这里不能顺手把真正执行验证的锁解掉。它还在干活，也还需要自己的执行名额。等待者退出，只能释放等待者自己的资源；当前验证是否成功，仍然由实际执行结果决定。

这部分代码在 cache_flight.rs。我给它留下了拥塞下的回归，检查等待者退出以后，后面的请求还能正常进来。

README 太热闹，真正的测试反而被漏掉了#

另一个问题比锁更普通。

wcode 会在仓库里找 proptest、hypothesis、quickcheck 这些框架的使用迹象，配合依赖声明决定哪些高级验证可以运行。早先这里复用了文本搜索的结果列表，最多取一千条。

我做了一个很小的仓库：前面的 Markdown 重复写了 1,100 行框架名，后面的 Rust、Python 文件才真的引用测试框架。结果，文档把那一千条名额吃完了，真正的源码使用证据没能进入发现结果。

还有一种更隐蔽的情况：同一个名字出现在两种语言里。Rust 文件里的 quickcheck 很多，R 文件里的 quickcheck 很少。按匹配行数截断，也会把后者挤掉。

这次我把框架发现需要的信息收窄了。它只记“这个查询在这种源码语言里出现过”，不再保留一大串重复文本。普通搜索仍然提供原来的分页结果；发现验证工具时，才走这条按查询和语言保留证据的路径。

扫描也放到独立的有界 I/O 池里。回归会先占满全局 Rayon 池，再检查框架发现能不能自己完成。只要它又偷偷依赖回全局池，测试就会卡住并失败。

这个改动的消融很直接：换回旧实现，那份 1,100 行文档的用例会失败；恢复新实现，同样的用例通过。比单独写一个“搜到了 proptest”的测试有用得多。

根目录已经查过，就别再查一遍#

项目里同时有 Rust、Python、Node 时，wcode 还要知道验证工具属于哪个项目根。否则一个子项目装了工具，另一个子项目也可能被误写成能运行。

这里我又找到了一个重复。先查整个 workspace，再处理根目录 . 时，会重新做一次相同的工具发现。重复声明两个 .，同一个请求里就会查三次。

我把本次请求已经取得的根目录结果留下，子项目仍然单独查。回归除了数调用次数，还比较 provider、缺口和截断状态，防止为了少扫一次把信息丢掉。两个重复根声明的例子，现在只查一次。

我没有把这份结果做成跨请求的长缓存。工具可能刚装好，manifest 也可能刚改过。把一个请求里的重复工作去掉就够了，没必要再引入一份难解释的新鲜度。

Windows 帮我抓到了另一种路径#

这轮 CI 还碰到了 Windows 的规范化路径问题。

OSS 源码归属检查会把编译目标做 canonicalize，再确认它仍然在 checkout 里。目标和 checkout 如果不是同一种路径表示，合法的仓库内文件也会被拒绝。现在两边都先规范化，再做边界判断，仓库外的源码仍然要拒绝。

后面又碰到一个更小的差异：cargo package --list 在 Windows 上给出了反斜杠路径，测试却拿它和 src/lib.rs 比较。包已经正常生成，检查仍然报缺文件。这次只在列表成员比较时统一分隔符，源码边界检查照常保留。修正放在这一笔提交。

并发回归的压力也保留了：每类操作 16 个请求，混合请求的原有 40 秒期限没有因为失败而往后挪。测试失败时，我希望先看到等待发生在哪里。

这轮并发修复在 macOS 上跑完了 1,863 项库测试，另有 7 项原本就需要手动运行的测试被忽略。Linux、macOS、Windows 和 OSS 打包还有各自的 CI，状态可以直接看 PR。这里记录的是一次发布前的修正，不把本地通过写成所有平台都已经验收。

做完这些，我对并行工作有了一个更实际的要求：几个 Agent 同时进来时，界面应该一直说得清楚，谁在执行、谁在等、谁需要重试。否则再多几个并发名额，也只是多几个人一起盯着加载图标。
