wcode 近况：从 0.9.0 到 0.9.15

上一篇版本文章还停在 10 月 2 日的 0.9.0。这段时间代码和文档一直在更新，博客落下了一截。到 11 月 16 日，公开发布版已经是 0.9.15，这里把中间十五个补丁版本的主要变化补上。

0.9.0 当时写了任务领取、改动验收和工作台。继续做下去，问题越来越具体：测试通过以后改了 Git 暂存区，结果还算不算当前的？没有测到耗时，界面为什么显示 0 ms？点一个文件，为什么只展开了文件区域，却没有找到那个文件？

这轮迭代花了不少力气处理这些细节。它们直接影响人能不能相信界面，也影响 Agent 下一步会不会重复劳动。

第一次接触这个项目，可以先看项目介绍。wcode 用 Rust 编写，通过 MCP 给编码助手提供仓库工具；模型仍由你使用的编码助手提供。本文按已发布的 0.9.15 整理，后续主分支和开发分支的变化另算。

先把已经做过的检查算对#

“检查通过”后面其实跟着一串条件：检查的是哪份代码、哪份设计，按哪条策略运行，结果从哪里来，现在还能不能查到。

0.9.8 把设计一致性页面缺少的真实数据补了进去。此前浏览器测试用的数据里有验收条件和约束，真实项目快照却没有完整带上这些字段。于是界面看起来有那一行，实际使用时却总像是没有声明、没有计划。这种问题只看演示数据很容易漏掉。

现在可以从需求继续查到验收条件，再看每条检查是否有映射、有没有运行、结果是什么、是否仍适用于当前版本。一个声明过但没有执行结果的检查，也会留在列表里。

0.9.9 又补了证据判定的几处边界。一个容易忽略的例子是 git add：源码文件可以完全没变，但 Git 的 index 已经变了。空提交也能改变 HEAD。只对比代码内容和设计内容，会漏掉验收所依赖的 Git 身份。

因此，在工作区有 Git 身份时，验证计划要检查证据记录及回执与当前身份是否一致。策略变了，旧策略下的结果也不能直接满足新计划。复用检查时，如果原始证据已经不在当前保留范围里，界面不能继续把它显示成一次当前有效的通过。

报告里还把“这次实际执行”与“复用了已有结果”分开了。复用有价值，省下来的执行也应该看得见；读报告的人需要知道结果到底是怎么来的。

这些变化见 0.9.8 和 0.9.9。

没有观测，不该显示成 0#

这几版里反复修的一类问题，是前端把缺失值变成了一个看起来很确定的数字。

场景现在应当表达的状态
没收到某项检查的耗时耗时未知
没有读取到 diff 的行数统计增删行数未知
没有样本，或者没有可用分母无法计算比例
检查已声明，但还没有执行记录缺少结果
验证计划对应另一份代码版本已被当前版本取代
命令没有可用的结构化失败位置无法定位到具体行

真正测得 0 ms，和根本没有计时，是两件事。显示成同一个零，人就容易把“没有观察到”读成“没有问题”。

0.9.8 到 0.9.12 把这类处理补到了检查耗时、任务计数、图谱覆盖、变更统计和证据状态里。显示百分比的地方也保留各自的分子和分母，避免一个百分数脱离它原本衡量的对象。

图谱同样要说明自己是哪一份。原来选择的是“最新图谱”，后来新的快照出现，旧视图就应该显示过期；如果我明确固定了某个历史快照，它可以继续展示，但要保留那个历史身份。

我希望看到的状态足够具体：没跑，就告诉我没跑；跑失败了，就给出失败；结果过期了，就告诉我需要重新检查什么。

从问题一路走到代码#

工作台这次改动比较大，但关注点很实在：发现一个问题以后，能不能沿着它继续查下去。

0.9.3 给代码阅读器补了符号大纲、定义范围和行号跳转。变更里的定义如果有显式的需求映射，也能看到对应需求。这里保留了精度边界：diff 行范围与符号重叠，只说明它们的位置相交，不能直接当作完整的语义影响分析。

0.9.7 把命令面板和导航接到了具体对象上，可以搜索需求、组件、文件、任务、证据和符号。调查位置进入 URL hash，前进、后退可以回到刚才的位置。

到 0.9.12，界面整理成左侧对象导航、中央内容、右侧检查器，底部共享 Problems、Jobs、Logs、Evidence。看失败记录时能继续找任务输出，再回到源码；工作区、版本和连接状态有独立位置，窄屏里也需要看得见。

0.9.15 修了一个很小却很烦的问题：在导航里选中文件，要真正滚动并聚焦到文件树中的那个条目。如果旧筛选把目标藏住，就清掉筛选；如果目标在折叠的后续条目里，就展开到能看到它。

文件树的首批渲染也限制为 200 个条目，并写明显示了多少，剩下的由人展开。大仓库不需要一打开就把所有节点灌进页面。换工作区或换查询时，展开状态重新收起，避免旧状态影响新结果。

这些交互可以看 0.9.12 与 0.9.15 的说明。旧文章中的截图仍对应它们当时的版本。

长任务要留下能接着做的状态#

任务跑得久，换模型、刷新页面、断开连接，都可能发生。接回来时至少要知道：什么还在运行，哪些已经完成，哪些失败了，下一步依赖谁。

0.9.1 和 0.9.2 整理了保留任务、任务来源筛选、输出搜索和按 task ID 重新观察的流程。连接中断以后，应当继续读取同一个任务的结果。看不到输出就再启动一遍命令，会把一次网络问题变成两份运行中的工作。

0.9.11 修了计划历史保留中的另一个问题：如果只按总数量修剪历史，某个较少更新的计划可能连最新状态都被删掉，已经领取或完成的任务就可能被重新看成 Pending。现在保留每个计划的最新快照，让进度仍然有地方可查。

0.9.13 让计划显式关联 Worklist 项，检查引用的 ID。任务目标或范围发生变化时，执行状态会要求重新规划，并保留原来的批准边界。

0.9.14 则把需求收敛放到首页和终端观测里：哪些稳定，哪些正在变化，哪些还需要处理。打开后就能看到未完成工作的分布，再决定往哪里查。

这些状态帮助接手者继续工作；Worker 写下的完成报告，仍需要对应版本的检查证据来支持。

少搬上下文，也少做重复计算#

性能方面，这轮主要在删重复工作。

0.9.4 到 0.9.6 清理了图查询、diff 排序和仓库映射里反复生成小写字符串等不必要分配。0.9.7 给几个返回较重状态的工具提供默认摘要，同时明确告诉调用方省略了什么、到哪里继续读。

摘要的作用是让第一轮看到足够决定下一步的状态。源码正文、编辑用的 SHA、失败信息和必要约束，仍然各自有明确的读取入口。

0.9.12 复用缓存的图快照，减少每次读取都深拷贝的开销。0.9.14 则处理上下文压缩时的重复序列化：调用方已经算过字节数，压缩过程就复用这个结果；候选排序的评分也先算一次，再用于比较。

这些改动能解释工具内部少做了什么。要回答一次完整任务快了多少、模型账单少了多少，还需要固定任务、模型和运行条件去测。发布说明里的 JSON 字节测量不能直接换成 token 节省，更不能当作任务成功率。

具体实现分别放在版本目录里，博客就不把每个循环和分配都展开了。

把证据规则写成了一篇论文#

11 月 6 日，我把这条思路整理成了预印本：WCode: Revision-Bound Evidence for Stateful Software Agents，署名 Francis Du。

论文关注的是一份结果要带上什么信息，才有资格支持当前的软件修改：它针对谁，由谁产生，覆盖什么，按什么策略执行，又绑定哪一份代码和设计。

实验用了四种语言的 60 个开发者编写的合成场景，在不同响应预算、缓存阶段和重复条件下取得 2,520 次测量调用；另外重放了 22 个选定的契约反例，并检查了 11 项操作控制。

这个范围需要说清楚。它检验的是所选运行时契约，尚未给出独立真实仓库的 Issue 解决率，也没有证明完整 Agent 相比其他产品的胜率。论文绑定 11 月 6 日保留的实验版本；本文介绍的后续功能，不能回填成当时已经测过的能力。

页面提供中英文 PDF、LaTeX 源码、构建说明和校验和。有兴趣看实验怎么做，可以直接从那里往下读。

升级后，记得看正在运行的进程#

日常升级可以先看当前版本，再运行：

wcode --version
wcode update
wcode --version

wcode update 选择执行时的最新稳定版。要固定到 0.9.15，使用该版本的下载文件和对应的 SHA256SUMS；更新命令没有 --version 选项。

替换磁盘上的可执行文件以后，还要重连 MCP 客户端；独立运行的服务则先检查活动任务，再安排重启。确认新进程使用的路径和版本，才能知道实际跑的是哪个安装。

权限方面也要同步看当前文档：这些版本的命令策略和授权默认宽松，不能继续按早期文章理解成“所有命令默认逐条审批”。操作系统沙箱是按调用选择的，后端不可用时可能回退为直接执行。只做被动检查时，文档给出的组合是 --read-only --no-exec --no-semantic；其中 --no-exec 仍覆盖会话命令授权。Workspace 文件边界、SHA 编辑检查与命令执行限制各自起作用，配置方法见安全文档。

0.9.15 的发布还更新了 rustix、quinn-proto 和 quinn-udp 的修补版本。源码发布、平台安装包和正在运行的服务有各自的状态，检查时要落到实际使用的那个版本。
